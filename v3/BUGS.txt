 [BUG-001] 上部バーの URL 欄・右端ボタンがタブ列と重なっていた
--------------------------------------------------------------------------------
 症状  : 診断ログの座標比較で
             UI rect top-tab-5 = 254,160,282,182   (タブ列の右端 x=282)
             UI rect top-url   =  36,160,976,182   (URL 欄の始点 x=36)
         となり、URL 欄がタブ列の真下にレイアウトされていた。
         併せて「タブ列の右端でクランプ」という保護も機能しておらず
         (条件が rightX < 8+8 = 16 となり常に不発)、ウィンドウを
         狭くすると右端の 4 ボタンもタブ列に重なる状態だった。
         現状の幅ではタブが先に描画され HitTest も先勝ちだったため
         視覚上は無傷に見えていた — 「たまたま成立していた」レイアウト。

 原因  : include/UI/ImGuiOverlay.hpp  drawTopBar() のタブ列
             tabsEnd = ImGui::GetCursorPosX();   // ImGui::Button の直後
         ImGui::Button() の内部で走る ItemSize() (imgui.cpp) は
             window->DC.CursorPos.x =
                 window->Pos.x + window->DC.Indent.x + ColumnsOffset.x
         と「次の行の行頭」へリセットしてくる。そのため
         GetCursorPosX() は必ず行頭 (= WindowPadding.x = 8) を返し、
             urlX     = 8 + spacing*1.5 = 20  → 画面 x = 16 + 20 = 36
             クランプ = rightX < 8 + 8       → 常に不発
         となる (実測 36 と算術が完全一致)。
         コメントに「SameLine() は毎回行頭へ戻す」とあったが、
         行頭へ戻すのは SameLine() ではなく ItemSize() の方だった。

 修正  : SameLine() で「前ボタンの右端 + ItemSpacing」へ戻した後で
         tabsEnd を取得するよう変更し、コメントも実態に合わせて修正。

 状態  : 修正済み — 再テスト合格
             修正前  url left=36   (tab right=282 と重複)
             修正後  url left=302  (tab right=282 の右、幅 674)
                     open left=1067
 検証  : v3_t14_open.ps1  "--- 2. BUG-A layout ---"
         回帰チェック: top-url / top-open が top-tab-5 の右側にあること、
         URL 欄の幅が 180px 以上であること、修正後もタブが押せること。

 [BUG-002] 「複数開く…」で再生が始まらなかった
--------------------------------------------------------------------------------
 症状  : 起動直後に上部バー / ポップアウトの「複数開く…」でファイルを選ぶと、
         リストには追加されるが再生が一切始まらない
         (ボタンを押したのに何も起きない)。

 原因  : src/main.cpp  processUiActions() の UiAction::OpenFiles
             const bool wasEmpty = core.vlc->playlist.empty();
             core.vlc->playlist.addMany(paths);
             if (wasEmpty) openInput(core, paths.front());
         openInput() はプレイリストが空のときだけ 1 件シードするため、
         起動直後 (シード済み) には wasEmpty が必ず false になり、
         openInput が呼ばれない。
         根本原因は、上部バー/ポップアウトの「複数開く…」(開いて再生)
         と操作パネルの「ファイルを追加…」(追加だけ・再生は継続) が
         同じ UiAction::OpenFiles を共有しており、
         2 つの異なる操作を 1 つのハンドラで表現できていなかったこと。

 修正  : UiAction::OpenFilesPlay を新設し、「複数開く…」2 箇所
         (上部バー kRight[1] / ポップアウト) をこれに付け替え。
         「ファイルを追加…」は従来どおり OpenFiles (追加のみ) のまま。
         ハンドラは両者を 1 case にまとめ、
             OpenFilesPlay → 常に先頭の 1 件から再生を開始
             OpenFiles     → リストが空のときだけ再生を開始
         と分岐。リストへの追加は両方とも addMany で行う。

 状態  : 修正済み — 再テスト合格
             input: open OK  1920x1080 ... (再生開始)
             playlist: 2 件を追加 (計 4 件)
 検証  : v3_t14_open.ps1  "--- 4. BUG-B open multiple files ---"
         (実際のファイル選択ダイアログに 2 ファイルを指定して操作)

 [BUG-003] Ctrl+O / URL 欄で開いたファイルとプレイリストが同期していなかった
--------------------------------------------------------------------------------
 症状  : 起動後に URL 欄 (または Ctrl+O) で別のファイルを開いた直後、
         P (前へ) / N (次へ) が再生中ファイルと無関係な項目に飛ぶ。
         リストが 1 件しかない状態で URL 開放すると、P は完全に無反応。

 原因  : src/main.cpp  openInput() がプレイリストを触るのは
         「空のときだけシードする」処理のみで、index を
         現在再生中の入力に合わせるコードが存在しなかった。
         そのため Ctrl+O / URL で開いたファイルはリストの
         現在位置に反映されず、Playlist::move(delta) が
         古い index を基準に前後していた。

 修正  : tools::Playlist に setOrAdd(path) を追加
             - 現在位置が既に一致  → 何もしない (同名 2 件でも「次へ」が
                                      跳ね返らない)
             - リスト内にあれば    → その番号へ移動
             - 未登録なら          → 末尾に追加して番号を合わせる
         openInput() の再生成功時に呼ぶよう変更し、起動時のシード処理
         (メインと拡張ロード時の 2 箇所) も setOrAdd に統一。
         既に index が正しい経路 (次へ/前へ/ジャンプ/終了時自動送り) では
         現在位置が一致するため、挙動は変わらない。

 状態  : 修正済み — 再テスト合格
             URL で small_320x180.mp4 を開く
             → P で test_60s.mp4 (起動時シード)
             → N で small_320x180.mp4 に戻る
             → 複数開くで 2 件追加 → N で test_1080p_h264_aac.mp4
 検証  : v3_t14_open.ps1  "--- 3. BUG-C url open -> Prev -> Next ---"

 [NEW-001] FSR で画面外まで拡大されてしまう / ガタガタ (要件 ①⑤)
--------------------------------------------------------------------------------
 症状  : FSR (EASU) 有効時に映像がビューポート外へはみ出し、
         動きがカクつく・ギザギザに見える。
 原因  : src/Core/VideoRenderer.cpp  drawVideo() の EASU 3 パスで、
         パス① (mainPS → 入力 RT) とパス② (EASU → 出力 RT) が
         ビューポートを明示設定せず、既定の「ウィンドウ実寸」のまま
         ラスタライズしていた。EASU は出力ピクセル座標を入力テクスチャ
         座標へ写像するため、ビューポートが中間 RT の実寸より大きいと
         「RT の外側に対応する入力領域が存在しない」マス目ができ、
         画面外へ引き伸ばされたように見える。
 修正  : ViewportScope (RAII) を導入してパスごとに明示
             パス全体 : RT 実寸
             パス①    : m_fsrSrcW x m_fsrSrcH (映像の実寸)
             パス②    : m_fsrDstW x m_fsrDstH (表示矩形の実寸)
             RCAS     : 出力 RT 実寸 (定数 con.x は無変更)
 状態  : 修正済み — 再テスト合格
             VideoRenderer: FSR viewport easu=320x180 -> 948x533 (rt=1408x792)
             (修正前は pass① が rt=1408x792 でラスタライズされていた)
 検証  : v3_t8_settings.ps1  phase B
             - pass1 ビューポート = 映像ソース実寸 (320x180)
             - pass1 ビューポート ≠ ウィンドウ実寸
             - pass2 ビューポート = 表示矩形 (ソースより大きい)
 ※ 実機 (NVIDIA/AMD) が無いため画質は「理論上動作する」水準 (ユーザー承知)。

 [NEW-002] フレーム生成の補間が不正確だった (要件 ②)
--------------------------------------------------------------------------------
 原因  : main.cpp の frameBlend() が補間重みを「表示フレーム番号 /
         量子化係数」で求めていたため、表示レートと映像の実 pts が
         一致しない瞬間に位相が跳ね、補間の刻みが粗くなっていた。
 修正  : frameBlend() を削除し、draw() の引数を float blend →
         double mediaTime に変更。
         VideoRenderer::interpolationWeight(mediaTime) が
         保持している prev/curr の実 pts から連続計算する
             w = (mediaTime - prevPts) / (currPts - prevPts)
         (clamp 0..1、区間が異常なら EMA のフレーム間隔へフォールバック)。
         m_prevPts は swap の直前に保存。
         「目標倍率 N が表示フレーム数より大きいときだけ N 分割へ
         量子化する」ようにし、そうでない場合は連続補間のまま。
         ディスプレイ間隔は draw() 毎の steady_clock EMA (α=0.1)。
         停止中は interpolationWeight を使わない (blendPass(1.0))。
 検証  : 補間の良し悪しは自動判定できないため、再生回帰 (t3/t5/t13) と
         心拍 (frame=) で「壊れていない」ことを確認。

 [NEW-007] 暗号化 DVD を VLC の dll で読めるようにする (要件 ⑧)
--------------------------------------------------------------------------------
 方針  : 「DVD を読み込んで暗号化を検知したら VLC の dll を読み込んで
         再生する」(ユーザー確認済み)。暗号が無ければ従来どおり
         FFmpeg 経路を使い、既存コードは変更しない。
 検出  : src/Extensions/VlcVideo.cpp  detectDvd()
             VIDEO_TS ディレクトリ / .IFO / .VOB / .ISO / ドライブルートを判定
             VIDEO_TS 内の VTS_xx_1.VOB の先頭 64 セクタ (2048 B) に
             MPEG-PS パックヘッダ 00 00 01 BA が 1 つでもあれば暗号なし、
             1 つも無ければ CSS スクランブルとみなす。
             .ISO は中身を読めないため「判定不能 → VLC」扱い。
             判定不能 (読めない等) のときは FFmpeg 経路へフォールバック。
 ロード  : findLibvlc() が HKLM/HKCU の Software\VideoLAN\VLC InstallDir →
           標準インストールパスの順に libvlc.dll を探し、
           LoadLibraryExW(LOAD_WITH_ALTERED_SEARCH_PATH) で読む
           (libvlccore.dll / plugins\ を同ディレクトリ基準で解決)。
           必要シンボル 20 個を GetProcAddress で動的解決。
           無い環境では理由を明示してエラー終了 (黙って黒画面にならない)。
 再生  : libVLC の video callback で BGRA を「2 バッファ + mutex」で受け、
         D3D11 テクスチャへ UpdateSubresource して既存の VideoRenderer へ
         流し込む (UI / レターボックス / 全画面 / 字幕レイアウトはそのまま)。
         音声は libVLC 自身の WASAPI 出力 (AudioEngine は停止)。
 結合  : VideoDecoder::setExternalStatus() で currentTime() / info() を
         上書きし、UI のシークバー / 情報タブ / 終端検出をそのまま動作。
         シーク・ポーズ・音量はレンダループでエッジ検出して libVLC へ転送。
         'vlc:<path>' プレフィックスで強制的に VLC 経路へ切り替え可能。
 状態  : 実装済み — 再テスト合格
 検証  : v3_t15_dvd.ps1
             1) クリアな VIDEO_TS → encrypted=no → FFmpeg 経路のまま、
                libvlc.dll は読み込まれない
             2) スクランブルした VIDEO_TS → encrypted=yes →
                "dvd: encrypted -> loading the VLC dll" →
                "VLC: libvlc.dll loaded  version=3.0.24" →
                "VLC: media attached" → "input: open ... (libVLC)"
                (合成ディスクなので再生自体は失敗するが、検出 → 読込
                → エラー報告の経路は成立している)
             3) vlc:test_60s.mp4 → "input: open OK (libVLC)" →
                Space "Shortcut: pause (libVLC)" →
                右矢印 "VLC: seek ->" → Space "Shortcut: resume (libVLC)"
             4) 3 実行とも FATAL なし
 ※ 暗号化 DVD の実物は無いため、検出 → ロード → 再生経路は合成データで
   確認。CSS 復号そのものは libVLC (内蔵 libdvdcss) に委ねる。

 [NEW-009] fps が上がらない (フレーム生成 / 高フレームレート素材)
--------------------------------------------------------------------------------
 症状  : 30/60/120/240fps 比較クリップで見たフレームレートが常に 60 fps で、
          フレーム生成を有効にしても変化しなかった。
 原因  : 描画レートを GetDeviceCaps(VREFRESH) の固定値 (60 Hz) でスリープ
          していた。コンテンツ fps もフレーム生成も一切反映されない。
          さらに Windows の既定タイマ分解能は 15.6 ms で、サブ 16 ms の
          スリープは物理的に合わない。
 修正  : 1) ソースの瞬間フレームレートを VideoDecoder のデコードスレッドが
              publishFrame() (= コンテンツ順の全フレーム) で測る EMA を追加。
              描画レートから測ると「描画が遅い → 測定値も下がる」という
              自己制限 (フィードバック) になるため、描画に依存しない位置で測る。
          2) target = clamp(source x (frameGen ? factor : 1), refresh, 500)
              を毎フレーム再計算する。変化時のみ
              main: present target -> 120 Hz  source=30 fps  frameGen=on x4
              をログする (1 Hz 以下の揺らぎはログしない)。
          3) timeBeginPeriod(1) でタイマ分解能を 1 ms にし、
              「Sleep で粗く待ち + 残りを QPC スピン」で待つ方式に変更。
 参考  : オンライン仕様の確認
          - Present は syncInterval=0 で呼んでいるため、DWM 合成下でも
            リフレッシュレートを超えて呼び出せる (画面には最新フレームが

 変更 5: 配布用インストーラー (MSI) を追加した

 変更内容:
   - WiX Toolset v5 (dotnet tool) で per-user の MSI を作る構成にした。
     installer/installer.wxs に定義、installer/build_installer.ps1 が

     テストはログ (stdout) が必須だが、ユーザーにはコンソール窓を出したくない
     ため、ログの出力 (NANOALPHA_CONSOLE) とサブシステム (NANOALPHA_CONSOLE_WINDOW)
     を別オプションに分離した。GUI サブシステムでも stdout ハンドリは
     引き継がれるのでパイプで起動すればログが読める (実測 4221-51 行)。
     /MT なので VC 再頒布パッケージにも依存しない。
   - アプリアイコンと VERSIONINFO を resources/nanoalphaplayer.ico /
     resources/app.rc で追加した (make_icon.ps1 が PNG 込み ICO を生成)。
   - 同梱ランタイムは exe が実際に import する 5 DLL のみに絞った
     (avformat-63 / avcodec-63 / avutil-61 / swresample-7 / swscale-10)。
     avdevice-63 / avfilter-12 と ffmpeg.exe / ffplay.exe / ffprobe.exe は
     未使用なので除外した (ffplay だけで 18 MB)。
   - installer/test_installer.ps1 を追加 (23 系統目)。

 留意点 1: per-user と per-machine の切り分け
   - per-machine (Program Files + HKLM) にすると管理者権限が無い環境では
     エラー 1603 で必ず失敗する (実測)。UAC が一切不要な per-user を採用した。
   - WiX の Package/@Scope は perUser / perMachine / perUserOrMachine の3種。
     perUserOrMachine は ALLUSERS=2 + MSIINSTALLPERUSER=1 になるが、
     MSI ドキュメントのとおり MSIINSTALLPERUSER は ALLUSERS が 2 のとき
     にしか効かない。WiX は Property/@Value に空文字列を入れてくれない
     (WIX0006) ので、ALLUSERS="" による per-user の明示は authoring できない。
   - StandardDirectory の候補に CommonDesktopFolder は無い (WIX0021)。
     使う場合は素の <Directory Id="CommonDesktopFolder" /> で参照する。

 留意点 2: per-user なのに ARP エントリが HKLM に出ていた
   - Scope="perUser" で入れると配置先もレジストリ (HKCU/HKCR) も
     ユーザー側に正しく書かれるのに、Windows Installer が作る
     「プログラムの追加と削除」キーだけが
     HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall に
     出てしまう (実測)。このままだとアンインストール時に UAC が出る。
   - そこで ARPSYSTEMCOMPONENT=1 で Windows Installer 自身のエントリを
     非表示にし (キー自体は作られるが ARP には出ない)、HKCU に完全版
     (DisplayName / Publisher / DisplayVersion / DisplayIcon /
      InstallLocation / UninstallString / NoModify / EstimatedSize) を
     インストーラーが直接書く構成にした。アンインストール文字列は
     MsiExec.exe /X{ProductCode} で UAC なしに消える。
   - ProductCode を固定しないとビルドのたびに別の製品として扱われ、
     前版が残ったままになる (/x が 1605 = 製品が見つからない)。
     0.1.0 は ProductCode="{5C9E2B41-7D08-4A63-9E15-2F6C8B4D7A90}" で固定した。

 留意点 3: WiX のその他の罠
   - XML コメントに "--" を書けない (={3,} に置換した)。
   - 属性の中で <?echo $(var.Ext)?> は使えない → $(var.Ext) を直書きする。
   - Package に InstallScope / Platform 属性はない
     → Scope="perUser" と CLI の -arch x64 で指定する。
   - MajorUpgrade に AllowDowngrade はない。
   - 標準ディレクトリは Directory ではなく StandardDirectory。
   - CustomAction の FileKey ではなく FileRef。
   - 出力オプションは -out (-output は不可)。
   - <?foreach?> はセミコロン区切り (カンマ区切りだと1回だけ回る)。
   - バージョン情報を持つ DLL が複数入るコンポーネントは Guid="*" を使えない
     (WIX0368) → ファイル群ごとにコンポーネントを分け明示 GUID を振る。
   - UI は <UIRef Id="WixUI_Mondo" /> ではなく
     <ui:WixUI Id="WixUI_Mondo" InstallDirectory="INSTALLDIR" />。
     UIRef だと WIX0094 (protection level) で落ちる。
